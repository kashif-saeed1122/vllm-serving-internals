I deployed a Qwen2.5-7B-Instruct-AWQ model on the vLLM 0.28.0 inference engine. vLLM uses dynamic, block-based KV cache allocation with a fixed block size of 16 tokens, which benefits the system in three ways: (1) no pre-allocation of the full worst-case memory upfront — blocks are allocated on demand as generation proceeds, eliminating internal fragmentation; (2) no external fragmentation, since every block is the same fixed size and any free block can serve any request; (3) memory sharing — identical, already-computed KV blocks are reused across iterations, with a shared block's presence tracked through a reference count until nothing references it anymore.

The sweep tested concurrency 1/2/5/10/20, each run with fixed input length 512, output length 256, --ignore-eos, and 100 prompts per run. The --seed value was fixed at 42 across every run — worth flagging, because it means every run generated the identical 100 prompts, so from run 2 onward the prefix cache hit rate was high in every case, not because of concurrency but because the same content was being replayed against an already-warm cache. This is the flaw that made most of Week 2's TTFT numbers unreliable, corrected in Week 4 with a unique seed per run.

TTFT depends on prefill compute (how many tokens actually need processing — the thing cache state controls directly), queueing/admission delay under concurrency, network round-trip, and server/warm-up effects. In Week 2, TTFT mean at conc=1 was 98.41ms, dropping sharply to 24.36ms at conc=2 — because conc=2's run replayed prompts conc=1 had already cached. From conc=2 to conc=20, TTFT climbs gradually (24.36ms→71.38ms), and since every run shares the same seed, this growth isn't prefill cost rising — it's queueing delay as more requests compete for the scheduler at once. At conc=20, the tail is notably worse than the mean (p99 128.50ms vs 71.38ms mean) — the same left-skew pattern that shows up more sharply in the clean Week 4 curve.

ITL and TPOT are far less sensitive to cache warmth than TTFT — but not literally constant: Week 2's own numbers show ITL mean rising 8.826ms→12.033ms (36%) across conc 1→20, and the clean Week 4 curve shows this more clearly (8.75ms→14.76ms, 69%). The correct read: ITL/TPOT are independent of cache state and startup effects, but do respond to concurrency — more sequences decoding simultaneously means more contention for memory bandwidth.

Throughput gain per concurrency-doubling shows diminishing returns: 1→2 = 2.06x, 2→5 = 2.42x, 5→10 = 1.81x, 10→20 = 1.66x. This matches decode being memory-bandwidth-bound: batching amortizes the weight-read cost across more sequences, with returns shrinking as the bandwidth ceiling is approached. Caveat: this sweep shares Week 2's fixed-seed flaw, so these numbers carry a small residual cache boost — though duration is far less cache-sensitive than TTFT (Week 4 found only ~1.18x duration difference between fully-cold and fully-warm at the same concurrency, despite a 7-8x TTFT difference), so the diminishing-returns shape is likely a real concurrency effect.

TTFT is the metric that actually degrades in a way a user would notice — but the "conc=20 waits ~3x longer" figure, read off Week 2 directly, understates it, because both runs benefited from cache reuse unevenly. The clean Week 4 curve shows the real number: mean TTFT goes from 110.97ms (conc=1) to 1006.23ms (conc=20) — roughly 9x, not 3x. The corrected measurement shows the degradation is three times worse than the flawed data suggested, which is itself the clearest argument for why the reseeding fix mattered.

(Separately, I ran a memory-ceiling sweep at concurrency 8/16/32/48/64 with longer 6144-in/1024-out prompts — a distinct experiment targeting the pool's capacity limit, not this TTFT-vs-concurrency curve.)
