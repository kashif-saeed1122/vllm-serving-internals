## Metrics Glossary

**TTFT** — Time To First Token
**ITL** — Inter-Token Latency
**TPOT** — Time Per Output Token
**E2EL** — End-to-End Latency

### LLM inference has two phases (vLLM, TensorRT-LLM, TGI, etc.)

1. **Prefill phase** — the GPU processes all input prompt tokens in
   parallel to build the KV cache. Heavily **compute-bound**.
2. **Decode phase** — the GPU generates output tokens one at a time,
   autoregressively. Heavily **memory-bandwidth-bound**.

### Definitions

**TTFT** — wall-clock time from the moment the inference engine
receives the API request to the moment the first output token is
transmitted to the client.
Depends on:
- Prefill compute
- Scheduling / queuing delay

**ITL** — the time delta between the generation of output token *i*
and output token *i+1*, during the decode phase.

**TPOT** — the arithmetic mean of all ITLs for a single request.
Represents the average decode speed for that specific generation.

```
TPOT = ( Σ(i=1 to N-1) ITL_i ) / (N - 1)      [N = total output tokens]
```
Example: ITL₁ = 2ms, ITL₂ = 2.5ms, ITL₃ = 3ms → TPOT = (2+2.5+3)/3 = 2.5ms

**E2EL** — total wall-clock time from API request receipt to
transmission of the final output token (or `<EOS>`).

```
E2EL = TTFT + (N_output_tokens - 1) × TPOT
```

### Throughput metrics (system-level, not per-request)

**Request throughput (req/s)** — number of fully completed inference
requests the system finishes per second.

**Output token throughput (tok/s)** — total number of output tokens
generated by the GPU per second, across all active requests.

## Paper Notes: PagedAttention
*(reading in progress)*

**Paper:** Efficient Memory Management for LLM Serving with PagedAttention

### Contributions (stated by the paper)

- Identification of the memory allocation problem in serving LLMs
- Proposal of the PagedAttention algorithm

### The problem

- Many concurrent requests → KV cache size increases.
- Processing LLM requests is an expensive operation.
- LLMs are autoregressive Transformer models — they generate tokens
  one at a time, and it is not possible to predict a sequence's final
  length/lifetime at the start of the request.
- **KV cache**: provides context from earlier tokens to generate the
  next token.

**Why do LLM serving systems fail to manage KV cache memory efficiently?**
→ They store the KV cache of a request in **contiguous memory space**.

Pre-allocating a contiguous buffer per request is a poor approach
because the KV cache grows and shrinks dynamically as the model
generates new tokens.

### The solution — PagedAttention

An attention algorithm that solves the KV-cache memory management
problem efficiently, by **not** storing the KV cache in contiguous
memory space.

```
Naive (contiguous) allocation:
[  Pre-allocated buffer                    ]
[  Used   | Idle | Gap (wasted, unusable)  ]

PagedAttention (block-based):
[Block A] [Block B]      [Block C] [Block D]   <- scattered in physical memory
    ^          ^              ^         ^
   AK1        AK2            AK3       AK4
                    |
              Attention Key (AK) - read via a block table,
              not by physical adjacency
```

### Issues it addresses and resolves

1. Internal fragmentation
2. External fragmentation
3. Enables memory sharing

**Note:** the crux of the PagedAttention algorithm is that it does
*not* store the KV cache in contiguous space.

### Findings

**1. Throughput scaling bends past concurrency ~5.**
Throughput-gain per unit of concurrency-gain: 1→2 is 2.06× (super-linear/noise),
2→5 is 2.42× (near-linear), 5→10 drops to 1.81×, 10→20 drops further to 1.66×.
Confirms Week 1's "5.7x throughput, no slowdown" finding was a true but
partial picture — the near-free scaling holds at low concurrency and
visibly degrades as concurrency climbs toward 20. This GPU/model/config
starts running out of easy headroom somewhere between concurrency 5 and 10.

**2. TTFT rises cleanly with concurrency — with concurrency=1 excluded.**
2→5→10→20 shows a clean monotonic increase (24 → 32 → 44 → 71ms mean),
consistent with more requests competing for prefill/scheduling slots as
load rises.

**3. Decode-step cost (ITL/TPOT) grows only mildly.**
8.8ms → 12.0ms mean ITL across a 20x increase in concurrency (36% growth)
while throughput grew ~15x over the same range. This is continuous
batching's mechanism made numerically visible: decode is memory-bandwidth-
bound, so batching more sequences into one step barely increases that
step's wall-clock time — tokens-per-step scales far faster than
time-per-step.

**4. Connecting thread:** aggregate throughput and per-token decode cost
both stay favorable through this whole range, but TTFT is the
user-facing metric that actually degrades — a request at concurrency=20
waits ~3x longer to see its first token than one at concurrency=2, even
though the system as a whole is far more efficient in aggregate.
Candidate framing for Month 3.

### Open questions (bound-your-depth — not resolved this week)

**A. `max_concurrent_requests` in the result JSON is exactly 2x the
configured `--max-concurrency`, at every level (1→2, 2→4, 5→10, 10→20,
20→40).** Too consistent to be scheduling jitter. Not yet traced to a
root cause in the tool's source — flagged for the Month 2 source dive
(this is literally request-lifecycle tracing, just pulled forward).
Other users online report the same exact 2x pattern independently, so
this looks like a real, versioned behavior of `vllm bench serve`, not
something specific to this setup.

**B. Concurrency=1's TTFT (98ms) is the highest of the whole sweep,
breaking the otherwise clean monotonic trend from concurrency=2 onward.**
Distribution is tight (std ≈13ms, all percentiles clustered 100-104ms) —
not just 1-2 slow outliers, the whole run ran consistently slow.
Leading hypothesis: one-time warm-up cost (CUDA graph capture for an
unseen batch shape, or GPU clock ramp-up from an idle power state)
specific to concurrency=1 being the first full 100-request run in the
sweep. Not confirmed. **Fix for Week 3:** add a small unrecorded warm-up
burst before the sweep starts, and consider re-running concurrency=1 a
second time at the end of the sweep to check whether the anomaly
disappears on a second pass.
