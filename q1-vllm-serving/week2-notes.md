## Metrics Glossary

**TTFT** — Time To First Token
**ITL** — Inter-Token Latency
**TPOT** — Time Per Output Token
**E2EL** — End-to-End Latency

### LLM inference has two phases (vLLM, TensorRT-LLM, TGI, etc.)

1. **Prefill phase** — the GPU processes all input prompt tokens in
   parallel to build the KV cache. Heavily **compute-bound**.
2. **Decode phase** — the GPU generates output tokens one at a time,
   autoregressively. Heavily **memory-bandwidth-bound**.

### Definitions

**TTFT** — wall-clock time from the moment the inference engine
receives the API request to the moment the first output token is
transmitted to the client.
Depends on:
- Prefill compute
- Scheduling / queuing delay

**ITL** — the time delta between the generation of output token *i*
and output token *i+1*, during the decode phase.

**TPOT** — the arithmetic mean of all ITLs for a single request.
Represents the average decode speed for that specific generation.

```
TPOT = ( Σ(i=1 to N-1) ITL_i ) / (N - 1)      [N = total output tokens]
```
Example: ITL₁ = 2ms, ITL₂ = 2.5ms, ITL₃ = 3ms → TPOT = (2+2.5+3)/3 = 2.5ms

**E2EL** — total wall-clock time from API request receipt to
transmission of the final output token (or `<EOS>`).

```
E2EL = TTFT + (N_output_tokens - 1) × TPOT
```

### Throughput metrics (system-level, not per-request)

**Request throughput (req/s)** — number of fully completed inference
requests the system finishes per second.

**Output token throughput (tok/s)** — total number of output tokens
generated by the GPU per second, across all active requests.

## Paper Notes: PagedAttention
*(reading in progress)*

**Paper:** Efficient Memory Management for LLM Serving with PagedAttention

### Contributions (stated by the paper)

- Identification of the memory allocation problem in serving LLMs
- Proposal of the PagedAttention algorithm

### The problem

- Many concurrent requests → KV cache size increases.
- Processing LLM requests is an expensive operation.
- LLMs are autoregressive Transformer models — they generate tokens
  one at a time, and it is not possible to predict a sequence's final
  length/lifetime at the start of the request.
- **KV cache**: provides context from earlier tokens to generate the
  next token.

**Why do LLM serving systems fail to manage KV cache memory efficiently?**
→ They store the KV cache of a request in **contiguous memory space**.

Pre-allocating a contiguous buffer per request is a poor approach
because the KV cache grows and shrinks dynamically as the model
generates new tokens.

### The solution — PagedAttention

An attention algorithm that solves the KV-cache memory management
problem efficiently, by **not** storing the KV cache in contiguous
memory space.

```
Naive (contiguous) allocation:
[  Pre-allocated buffer                    ]
[  Used   | Idle | Gap (wasted, unusable)  ]

PagedAttention (block-based):
[Block A] [Block B]      [Block C] [Block D]   <- scattered in physical memory
    ^          ^              ^         ^
   AK1        AK2            AK3       AK4
                    |
              Attention Key (AK) - read via a block table,
              not by physical adjacency
```

### Issues it addresses and resolves

1. Internal fragmentation
2. External fragmentation
3. Enables memory sharing

**Note:** the crux of the PagedAttention algorithm is that it does
*not* store the KV cache in contiguous space.
